# ADR-004 — 轮末建议标记采用链接引用定义格式

## 状态

已接受（memorial 003-turn-end-suggestion-buttons）

## 背景

「轮末建议按钮」功能（memorial 003）选定 D2 路线：模型按约定在回复中输出标记，客户端插件解析后渲染为输入框上方的快捷按钮。约束：

- 必须是纯客户端插件 + 提示词约定，不改 deepseek-harness 核心（仓库边界）。
- 标记会进入 assistant 消息正文，随消息流被一切渲染面消费：DSH 聊天、终端、以及未来任何 markdown 渲染器。
- DSH 聊天用自研 mdast→React 渲染器，DOM 有逐字节 fixture 钉死，插件不应改动它。

查证事实：该渲染器对**未引用的 link reference definition** 节点渲染空（definitions 只进入引用解析表）；对 **raw HTML 按字面文本渲染**（无 HTML 进入 DOM 的不可信输出策略）。

## 决策

约定模型在回复正文之后、仅在存在明确下一步时，输出最多三行链接引用定义作为标记：

```
[next-1]: <可直接作为下一条用户消息的完整文本>
[next-2]: <…>
[next-3]: <…>
```

- 客户端正则 `^\[next-(\d+)\]: <(.+)>$` 行级提取，序号升序取前 3。
- 含空格文本必须包尖括号（CommonMark destination 语法）；文本含 `>` 时该行解析失败，对应按钮不出现——优雅降级为"无按钮"。

## 否决的替代方案

- **HTML 注释 `<!-- … -->`**：本渲染器把 raw HTML 渲染为字面文本，注释将原样可见——直接出局。
- **围栏代码块 ```` ```dsh-suggest ````**：可行且鲁棒，但聊天里每轮尾部多一块可见代码，与正文建议重复，视觉噪音大。
- **前端启发式解析末段命令句**：零约定但误判/漏判率高，跨 agent 写作风格不稳定。
- **Host 端二次 LLM 生成**：每轮额外调用成本与延迟，且需改 host 端，超出纯插件边界。

## 后果

- 正面：标记在 DSH 聊天内自动隐形（definition 节点不渲染），同样隐形于 GitHub/VS Code 等标准 markdown 面；泄漏面仅剩纯文本终端（显示为 `[next-1]: …` 行）；渲染器与核心包零改动。
- 负面：模型偶发写坏格式 → 该轮无按钮（可接受；不重试不兜底启发式）；`>` 字符限制建议措辞；约定文案由插件注入控制，模型不守约时功能静默失效。
- 未来读者注意：`[next-N]: …` 行不是遗忘的引用定义，是功能契约；修改格式需同步注入文案、正则与本 ADR。
